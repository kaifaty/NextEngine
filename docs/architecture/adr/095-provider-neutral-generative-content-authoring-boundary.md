## Context

Next Engine plans to use generative tools for assets, maps and materials. A
prompt-centric integration would put nondeterministic provider behavior,
credentials, remote task IDs and changing prices next to deterministic project
composition. Direct provider output into project or runtime assets would also
bypass exact hashes, provenance/license closure, neutral validation and atomic
activation.

The existing engine boundary after source selection is already sufficient:
project authoring captures exact inputs; the cooker validates and hashes them;
`ProjectLockV3` binds the complete closure; runtime activates only the complete
candidate. The missing boundary is before cooking: typed intent, derivation,
resumable attempts, untrusted candidates, structural review and explicit
promotion.

Godogen demonstrates useful authoring and resumable-job patterns, while its
own simplification also shows that a rigid prompt/planner pipeline is not a
stable engine contract. The project remains a monitored upstream reference in
SPEC-46 rather than a dependency.

## Proposed decision

Adopt SPEC-46 as a `Proposed` provider-neutral, offline creator boundary.

1. Generators produce quarantined immutable candidates, never active project
   content or gameplay state.
2. Candidate reproducibility begins at captured output bytes and exact hashes;
   prompt/model/seed lineage is not a byte-reproduction promise.
3. Explicit structural validation, rights review and atomic promotion are
   required before generated bytes become ordinary project source.
4. Existing neutral cooking, exact project locking, packaging and activation
   remain the sole route from promoted source to runtime.
5. Provider credentials, opaque job handles, discarded outputs, mutable price
   tables and raw responses stay developer-local and out of public/runtime
   contracts.
6. Remote use is opt-in and billable submission is guarded by machine-enforced
   cost/attempt ceilings plus idempotent resume. Ambiguous non-idempotent
   timeout never auto-resubmits.
7. Structural checks are admission authority. Standardized previews and
   running-engine captures are report-only evidence.
8. Public commands/schemas are deferred until a bounded consumer proves their
   fields and limits under ADR-046.

The fallback is ordinary authored exact source through the current creator
workflow. Network/provider absence cannot block project work, runtime or v1.

## Product impact

Creators gain an auditable path to iterate on generated content without
turning the generator into an engine subsystem. Exact selected bytes remain
portable across tools/providers, failed or expensive attempts are resumable
without guessing, and generated content receives the same validation and
license treatment as hand-authored/imported content.

The first consumers are one PBR material set, one static prop and one bounded
three-chunk map, in that order. Full editor integration, a general world
generator, runtime generation, provider marketplace and generic job scheduler
remain outside scope.

## Relevant product checks

| Check | Scenario | Expected | Fallback |
|---|---|---|---|
| `GEN-MATERIAL-P1` | Generate, validate, preview and promote one captured material set. | Exact maps pass channel/scale/color/provenance checks and recook byte-identically; invalid candidate publishes nothing. | Author the same material through ordinary project source. |
| `GEN-ASSET-P1` | Promote one image-to-static-prop candidate. | Scale, pivot, topology, material, collider and B0 fallback closure pass existing content/package validation. | Use a hand-authored static prop. |
| `GEN-MAP-P1` | Promote one region/three-chunk route and run play/save/reload. | Persistent IDs, connectivity, dependencies, collision/navigation and streaming admission remain exact across regeneration and reload. | Use ordinary authored chunks and partition records. |
| `GEN-RESUME-P1` | Inject timeout, late status and repeated resume around one billable attempt. | No duplicate charge/submission or unverified promotion; ambiguous state stops explicitly. | Preserve the receipt/candidate and resolve manually or start a new attempt. |
| `GEN-PROMOTION-P1` | Inject tamper, rights, path, stale-base and publication faults. | Prior project and candidate remain intact; no partial promoted source. | Continue with the prior exact project source. |

These checks are planned and provide no current ProductCheck credit. Live paid
provider smoke is report-only; recorded responses and captured exact bytes
drive repeatable verification.

## Considered alternatives

- **Provider-specific public contracts.** Rejected because model names, APIs,
  job states and pricing change independently of engine content semantics.
- **Write generator output directly into project/runtime assets.** Rejected
  because it bypasses quarantine, provenance, neutral validation and atomic
  promotion.
- **Treat prompt plus seed as reproducible content.** Rejected because an
  external implementation or weights may change while the text remains equal.
- **Make the full agent/planner workflow normative.** Rejected because creative
  sequencing should evolve in skills/guides; only durable artifacts cross the
  architecture boundary.
- **Use screenshots as acceptance.** Rejected because pixels do not prove
  topology, units, collision, navigation, dependency or rights closure.
- **Introduce a generic scheduler first.** Rejected under ADR-046; a local
  bounded receipt/resume journal is enough for the first material consumer.

## Consequences

- SPEC-46 and ADR-095 remain `Proposed`; no implementation, public wire format,
  provider dependency or v1 obligation is created.
- Existing SPEC-03/17/24 exact-source and activation contracts gain an explicit
  future rule: they consume promoted bytes and never call a generator.
- Security and tooling specs gain cost, credential, rights, idempotency and
  recorded-fixture guardrails for future consumers.
- Map/material/render specs distinguish structural admission from optional
  visual proof.
- The first implementation plan starts with `GEN-MATERIAL-P1`; promotion to a
  current contract requires concrete bounds, focused negative coverage and an
  Accepted successor decision.

## Supersession

This ADR supersedes no Accepted decision. If a future consumer promotes any
part of SPEC-46, a successor ADR must name the exact current schemas/commands,
fallback and checks while preserving the provider-neutral candidate boundary.
