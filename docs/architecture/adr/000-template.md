# ADR-NNN: Краткое название решения

| Поле | Значение |
|---|---|
| ID | ADR-NNN |
| Статус | Proposed |
| Версия | 1.0 |
| Владелец | именованная команда |
| Дата решения | YYYY-MM-DD |
| Последняя проверка evidence | YYYY-MM-DD |
| Нормативные зависимости | ссылки на RFC/ADR |
| Заменяет | ID либо `отсутствует` |
| Заменён | ID либо `не заменён` |

## Контекст

Опишите решение, ограничения и проверенные evidence. Отделите факты от предпочтений.

## Решение

Сформулируйте одно decision-complete правило с MUST/SHOULD/MAY. Назовите source of truth, owner и публичную границу.

## Рассмотренные варианты

Для каждого варианта укажите причину принятия или отклонения и условия, при которых вывод изменится.

## Последствия

Перечислите обязательные изменения, ограничения, migration и failure semantics.

## Gate для Proposed частей

| Поле | Требование |
|---|---|
| Владелец | команда |
| Сценарий/команда | воспроизводимый вызов |
| Threshold | измеримый pass/fail |
| Evidence | manifest, logs, reports, media |
| Fallback | заранее выбранный вариант |
| Срок повторной проверки | дата или milestone |

Раздел MUST присутствовать, если хотя бы один элемент решения имеет статус `Proposed`. При отсутствии Proposed частей пишется `не применяется`.

## Supersession

Смысл Accepted ADR не переписывается. Новое решение создаёт следующий ADR, заполняет `Заменяет`, а старый документ получает только статус `Superseded` и ссылку `Заменён`.
