# 08 — Validation, performance and production promotion

## Purpose

Turn laboratory evidence into a bounded product decision. Earlier packages do
not make the feature current by accumulation.

## Production scenario required

Select one reference-game scenario with an observable loop, for example a
river crossing where water moves a rigid prop and repeated player/vehicle
passes deform one bank. Freeze exact non-goals, active region size, material
profiles, cadence, fallback and target hardware before implementation.

## Evidence set

- focused numerical corpus from packages 01–07;
- `play` with the production input/command path and no test mutation;
- `persistence-replay` across active, transition and corrupt cases;
- `content-package` for every new material/region authoring record;
- `platform` for GPU/render/backend changes;
- conditional Performance V5 workload with CPU/GPU/RAM/VRAM, particle/grid
  counts, iteration tails, staging charges and exact authoritative roots;
- Windows x86_64 and Linux x86_64 evidence on the same exact revision where the
  promotion claim requires both.

## Promotion checklist

1. Name the authoritative owner and exact mutable fields.
2. Choose CPU, GPU, recorded-result or reduced-model authority explicitly.
3. Add only the consumer-used engine-owned contracts and bounds.
4. Define command/query, fixed-stage commit and stable failure diagnostics.
5. Add the owner segment, save/load/restart, replay compare point and migration
   policy for the current alpha format.
6. Narrow ADR-058 without removing PhysX ownership of rigid/articulated state.
7. Update SPEC-02/03/21/25/26/30, routing, traceability and roadmap together.
8. Demonstrate identical `game`/`headless` semantics and complete fallback.

## Stop conditions

Do not promote if the product loop works only in a lab, GPU drift is hidden by
post-hoc tolerance changes, active/sleep conversion accumulates unbounded
error, the feature requires unbounded memory/iterations, or renderer state is
needed for collision/gameplay. Retain the accepted rigid/static fallback and
record the smallest unresolved discriminator.

## Research-only backends

DDFK, unified nonlocal variational solvers, neural Monte Carlo/operator
approaches, adaptive split/merge and full two-phase poromechanics may run as
bounded comparative spikes against the same corpus. They do not receive public
contracts or roadmap completion credit without a production consumer and a
strictly better measured trade-off.
